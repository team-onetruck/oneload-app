# Phase 0: 서울역 나침반 오차 실측 계획

라이브 뷰(카메라 배경 위에 방향 화살표를 얹는 모드)를 만들지 말지는 **폰이 읽는 방향이 서울역 지하에서 얼마나 맞는가**에 달려 있다.
이 문서는 그 값을 재는 테스트의 계획이다. 코드는 쓰지 않는다. 결과가 나오기 전에는 1단계(라이브 뷰 라이트)를 시작하지 않는다.

## 1. 왜 이것부터 재는가

- 화살표 각도는 `통로 방향 − 폰이 향한 방향`이다. 폰 방향이 틀리면 화살표가 그만큼 틀린다.
- 지하철역은 철골, 전기 설비, 스크린도어 때문에 자기장이 흔들려 수십 도 틀어질 수 있다. 이 정도 오차는 데모에서 "엉뚱한 쪽을 가리키는 화살표"가 된다.
- 한길의 원칙은 "확신에 찬 오답을 주지 않는다"(PRODUCT.md)다. 오차를 모른 채 화살표를 그리면 이 원칙을 어긴다.
- 현장 조사(사진 촬영)는 어차피 해야 하므로, 같은 방문에 이 측정을 끼워 넣으면 추가 비용이 작다.

## 2. 알고 싶은 것

| 질문 | 답이 쓰이는 곳 |
| --- | --- |
| 폰 방향이 실제 통로 방향과 평균 몇 도 다른가 | 1단계 진행 여부 |
| 오차가 지점마다 크게 달라지는가, 같은 지점에서는 일정한가 | "지점별 보정값"을 현장 조사 때 저장할 수 있는지 |
| 기종(iOS/Android)과 들고 있는 자세에 따라 달라지는가 | 지원 범위와 안내 문구 |
| 걷는 중에 값이 튀거나 서서히 밀리는가 | 화살표를 실시간으로 쓸지, 멈춰 있을 때만 쓸지 |
| 어느 구간이 특히 나쁜가 | 그 구간만 라이브 뷰를 끄는 방안 |

## 3. 성공 기준 (측정 전에 정해 둔다)

측정 후에 기준을 고르면 결과에 맞춰 기준을 바꾸게 되므로 지금 정한다. 숫자는 가정이고, 팀 합의로 바꿔도 되지만 **측정 전에** 바꾼다.

오차는 `|폰 방향 − 실제 통로 방향|`을 0~180°로 접은 값이다.

| 판정 | 조건 | 다음 |
| --- | --- | --- |
| **진행** | 전체 중앙값 ≤ 15°, 90번째 백분위 ≤ 30°, 45° 넘는 지점이 전체의 10% 이하 | 1단계 라이브 뷰 라이트 착수 |
| **조건부 진행** | 정확도는 부족하지만 같은 지점·같은 자세의 반복 편차(표준편차)가 ≤ 10° 로 일정함 | 지점별 보정값을 현장 조사에 포함하는 안, 또는 나쁜 구간만 끄는 안 검토 |
| **보류** | 위 둘 다 아님 (오차가 크고 불규칙) | 웹 라이브 뷰는 하지 않고 AR은 네이티브(VPS)로만 기획 |

## 4. 측정 대상

### 4.1 지점

현재 데모 지도의 노드를 기준으로 하되, **실제 현장 노드 목록은 현장 조사에서 정해지므로** 아래는 초안이다.

| 구분 | 지점 (데모 노드) | 이유 |
| --- | --- | --- |
| 개활지 기준 | 지상 출구 또는 역 밖 | 나침반이 정상인지 보는 기준점 (폰·앱 자체 문제 분리) |
| B1 | 1호선·4호선 개찰구 앞 | 통행량 많음, 환승 통로 |
| B2 | 공항철도 대합실, 직통열차 매표소, 직통열차 개찰구 | 목적지 경로의 중심 |
| B3 | 일반열차 매표기, 일반열차 개찰구 | 깊이 다른 층 |
| B7 | 승강장 (직통, 일반) | 스크린도어·열차 접근 |
| 이동 수단 옆 | 에스컬레이터 위·아래, 엘리베이터 앞 | 모터와 철골이 가까운 곳 |

목표는 **12~15개 지점**이다. 각 지점은 다음 중 하나로 실제 방향 기준을 얻을 수 있어야 한다.

### 4.2 기준 방향(ground truth)을 얻는 방법

실내에서는 정답 방향을 직접 잴 도구가 없으므로 **긴 직선 통로, 승강장 가장자리, 벽 축**의 방위를 지도에서 구한다.

1. 역 도면 또는 위성/지도 앱에서 해당 통로의 방위(북쪽 기준 시계 방향 각도)를 읽는다. 지하 통로는 지상 건물·선로 방향과 같다고 보고, 도면이 있으면 도면을 우선한다.
2. 통로의 어느 끝으로 향하는지(0° 또는 180° 모호함)는 현장에서 확인해 기록한다.
3. 지점마다 기준 방위와 출처(도면/지도)를 표에 적는다. 출처가 불확실한 지점은 분석에서 따로 표시한다.

한계: 기준 방위 자체에도 ±5° 정도 오차가 있다. 성공 기준(15°, 30°)보다 충분히 작아 감수한다.

## 5. 장비

| 항목 | 내용 |
| --- | --- |
| 폰 | iPhone 1~2대 + Android 1~2대 (기종·OS 버전 기록). 팀원 개인 폰으로 충분 |
| 방향 읽는 도구 | 기본 제공 나침반 앱 (iOS 나침반, Android는 기기 나침반 또는 신뢰할 만한 나침반 앱). **진북(true north)** 설정이 있으면 켜고, 모든 기기에서 같은 기준(진북 또는 자북+편각 보정)으로 맞춘다 |
| 기록 | 아래 6장 기록표 (스프레드시트). 지점·자세·기종·읽은 값을 현장에서 바로 입력 |
| 보조 | 긴 통로 방향을 찍어 둘 사진(사람 얼굴이 나오지 않게), 걸음 수를 세는 타이머 |

**알려진 한계:** 나침반 앱이 읽는 값은 브라우저(iOS Safari의 `webkitCompassHeading`, Android Chrome의 절대 방향 센서)가 읽는 값과 완전히 같다고 보장할 수 없다. 기기마다 센서 융합 방식이 다르다.
그래서 이 측정은 "센서 환경이 얼마나 나쁜가"에 대한 **1차 판정**이다. 결과가 '진행'이면 1단계 착수 전에, 같은 지점 몇 곳에서 브라우저로 한 번 더 재는 확인을 거친다. 이를 위한 임시 측정 페이지는 별도 개발 건이므로, 필요하다고 판단되면 그때 따로 승인받는다.

## 6. 측정 절차

### 6.1 준비 (현장 가기 전)

1. 지점 목록과 각 지점의 기준 방위, 보는 방향(어느 끝인지)을 정리한다.
2. 기록표를 만들고 팀원이 같은 양식으로 입력하게 한다.
3. 기종·OS 버전·나침반 앱을 확정한다.
4. 현장 촬영·측정에 역 운영 측의 사전 허가나 안내가 필요한지 확인한다. 필요하면 신청하고, 허가 없이 진행하지 않는다.

### 6.2 지점별 측정

각 지점에서 폰마다 다음을 한다.

1. **교정:** 폰을 8자 모양으로 흔들어 나침반을 교정한다. 교정 전 값은 기록하지 않는다.
2. **자세 A, 가슴 앞에서 세로로 들고 정면(통로 방향) 바라보기.** 라이브 뷰가 쓸 자세이다. 5초 안정되면 값을 읽는다.
3. **자세 B, 화면을 위로 향해 수평으로 들기.** 앱 따라 센서가 다르게 동작하므로 비교용이다.
4. 자세마다 **3회 반복**한다. 반복 사이에 폰을 내렸다 다시 든다(첫 값에 끌려가지 않게).
5. 읽은 값을 기록표에 적는다. 값 옆에 그 순간의 특이점(인파, 에스컬레이터, 열차 진입, 자석 가방 등)을 한 줄로 적는다.

지점당 약 3~4분, 12~15개 지점이면 **2~3시간**이다.

### 6.3 걷기 중 측정 (소수 구간만)

정지 상태 값만으로는 걷는 중의 흔들림을 알 수 없다. **긴 직선 통로 2~3곳**에서만 한다.

1. 통로 시작점에서 값을 기록한다.
2. 폰을 자세 A로 들고 천천히 통로 끝까지 걷는다. 걷는 동안 10초 간격으로 읽은 값을 동행이 받아 적는다 (혼자 폰을 보며 걷지 않는다).
3. 끝점에서 값을 기록하고, 시작-끝 값의 차이(밀림)와 중간 값의 튀는 폭을 본다.

### 6.4 안전과 예절

- 폰을 보며 걷지 않는다. 읽기는 멈춰서 하고, 걷기 측정은 동행이 기록한다.
- 통로 중앙, 개찰구 앞, 에스컬레이터 입구를 막고 서지 않는다. 한쪽 가장자리를 쓴다.
- 사람이 찍히지 않게 하고, 얼굴이 담긴 사진은 저장하지 않는다.
- 출퇴근 혼잡 시간대를 피한다. 가능하면 낮 시간 비혼잡 시간이 좋다. 다만 실제 사용 환경 비교를 위해 소수 지점은 혼잡 시간에 한 번 더 잰다.

| 기종 / OS | 예: iPhone / iOS 버전, Pixel / Android 버전 |

| 특이점 | 인파, 에스컬레이터, 열차 진입 등 |

## 8. 분석과 보고

1. 전체 오차의 중앙값, 90번째 백분위, 45° 초과 비율을 계산한다.
2. 지점별, 층별, 기종별, 자세별로 나눠 본다. 특히 B1·B2·B3·B7 층별 차이를 본다.
3. 같은 지점·같은 자세 반복의 표준편차를 구한다(보정값 가능성 판단).
4. 걷기 측정의 밀림 폭과 튀는 폭을 정리한다.
5. 3장 기준으로 **진행 / 조건부 진행 / 보류**를 판정하고, 근거 표와 함께 짧은 보고서로 남긴다.

## 10. 이 테스트가 말해 주지 않는 것

- 라이브 뷰의 사용성(들고 걷는 불편, 캐리어와의 병행)은 따로 봐야 한다.
- 화면에 얹을 화살표의 위치·크기·가독성은 디자인 문제다.
- 이 테스트가 '진행'이어도 네이티브 수준의 연속 위치 추적은 가능해지지 않는다. 노드 단위 방향 힌트까지다.
- 한국 내 시각 측위(VPS) 서비스의 커버리지와 비용은 별도 조사 대상이다.

## 11. 열린 질문

- 도면 또는 정확한 통로 방위를 어디서 얻을 것인가 (역 운영 측, 공공 데이터, 지도 앱)
- 현장 측정에 사전 허가가 필요한가
- 지원 기종 범위 (iOS만 먼저 볼 것인가)
- 판정 기준 숫자(15°, 30°, 45°/10%)를 팀이 그대로 쓸 것인가
