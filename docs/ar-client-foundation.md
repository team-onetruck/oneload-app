# 실제 AR을 위한 클라이언트 기반

## 현재 상태와 적용 범위

사용자의 목표는 실제 바닥에 고정되는 화살표다. 기존 `liveview.tsx`의 카메라·나침반 오버레이는 그 목표를 충족하지 않는다. 기존 웹은 유지하고, 네이티브 플랫폼 선정 전에 검증 가능한 공통 좌표·추적 보호 로직을 추가했다.

**실제 AR 동작 완료가 아니다.** 네이티브 추적기, 마커 검출기 축 변환, ARAnchor 생성·갱신, 실제 카메라 프레임 획득, 네이티브 렌더러는 아직 구현하지 않았다. 이번 작업의 입력과 출력 포트는 TypeScript 경계이며 Unity에서 바로 실행되는 플러그인이 아니다. Unity를 선택하면 같은 규약의 C# 구현 또는 명시적인 브리지가 필요하다. 테스트의 앵커·카메라·마커·품질 수치는 전부 합성 입력이다. 제품에 테스트 모드나 AR 진입점을 추가하지 않았다.

작업 시작 시 공유 `oneload-app`에는 서버 연결 단일화 관련 미커밋 변경이 있었다. 이를 복사·커밋하지 않고 `3f3b52b`에서 별도 worktree와 `feat/ar-client-foundation` 브랜치를 만들었다. 백엔드·Agent·지도·QA 저장소는 읽기만 했다. QA의 v0.3 및 추가 13장은 설계 참고로 읽었으며 팀 합의·구현 완료로 간주하지 않는다.

## 플랫폼 판단

권장 방향은 Android·iOS를 지원 목표로 두고 Unity + AR Foundation으로 한 단말에서 최소 실험을 먼저 수행하는 것이다. 사용자 비율을 추정해서 OS를 확정하지 않는다. 실제로 빌드·시험 가능한 단말 확보를 첫 순서로 둔다.

| 선택 | 판단 |
| --- | --- |
| Unity + AR Foundation | 두 OS의 공간 추적·앵커를 공통 API로 다루는 후보. Android ARCore XR Plugin, iOS ARKit XR Plugin과 각각의 실기기 검증이 필요하다 |
| React Native 중심 | 채팅·목록 UI에는 적합하지만 AR 엔진·네이티브 연결을 별도 해결해야 한다. 현재 웹을 먼저 이식할 근거가 부족하다 |
| 플랫폼별 Kotlin/Swift | 플랫폼 제어가 필요할 때 검토하되 두 구현의 유지·검증 비용이 생긴다 |

이 PC에서 확인한 것은 `adb` 설치, 연결된 Android 기기 없음, 일반 설치 경로의 Unity Editor 없음, 저장소 안의 Unity 프로젝트·AR SDK 없음이다. 기기 확보 전 지원 단말이나 OS 최소 버전을 확정하지 않는다. 로컬 iOS 빌드는 Mac·Xcode가 필요하며, 저장소의 macserver가 iOS 빌드를 할 수 있는지는 확인하지 않았다.

근거: [Google의 AR Foundation 안내](https://developers.google.com/ar/develop/unity-arf/getting-started-ar-foundation), [ARCore 지원 기기](https://developers.google.com/ar/devices), [React Native 네이티브 모듈](https://reactnative.dev/docs/turbo-native-modules-introduction), [Unity iOS 빌드 조건](https://docs.unity.com/en-us/engine/6000.7/manual/platform-specific/iphone/ios-building-and-delivering/build-process).

## 구현한 경계

| 파일 | 구현 내용 |
| --- | --- |
| `src/features/ar/types.ts` | 정규화된 촬영 프레임·검출·지도 마커·앵커·품질 정책 타입 |
| `coordinates.ts` | 포즈 합성·역변환, 마커 기반 yaw/이동 정합, 앵커 상대 지도 루트, 현재 카메라 지도 좌표 |
| `route.ts` | 실제 `RouteOut`의 waypoint·step 연결과 좌표 검증. 불완전하면 AR 기하를 만들지 않음 |
| `render.ts` | 유효 조건을 모두 통과할 때 통로 중점의 고정 화살표 한 개를 앵커 상대 포즈로 생성 |
| `presenter.ts` | 숨김 포트, 프레임 중단 감시용 tick, grace·재정합 수명, 비동기 요청 번호, 로컬 진단 순서 |
| `features/route/guide.ts` | 기존 `toActiveRoute`가 `arGeometry`에 서버 지도 버전·좌표를 보존하도록 연결 |

원시 검출기 포즈를 `MarkerObservation`에 그대로 넣으면 안 된다. [AprilTag의 포즈·좌표계 설명](https://github.com/AprilRobotics/apriltag#pose-estimation)처럼 검출기마다 카메라·태그 축이 다르다. 네이티브 어댑터는 축·단위·마커 앞면을 변환하고, 촬영 당시 포즈와 영상의 `frameId`, `capturedAtMs`, `arSessionId`를 함께 보존해야 한다. 현재 정합기는 이 값이 모두 같을 때만 합성한다. 검출 완료 시점의 최신 카메라 포즈로 바꾸는 입력은 거부한다.

내부 좌표는 미터, +y 위, +z 전방, 지도 yaw는 +z에서 +x 방향으로 증가한다. 마커는 수직 벽 설치, +y 인쇄물 위, +z 앞면 바깥쪽이며 검출에 사용한 실제 크기가 메타데이터와 일치해야 한다. 기울어진 마커의 전체 포즈 지도 계약은 별도 확장이다.

지도→AR 초기 정합은 yaw + translation이다. 정합 시 앵커의 역포즈로 `mapInAnchor`를 저장한다. 이후 프레임마다 최신 앵커 포즈를 합성한다. 렌더러는 `arrowInAnchor`를 해당 앵커의 자식으로 적용한다. 지도 루트 변환을 다시 곱하면 이중 변환이 된다. 현재 위치는 최신 앵커 기준 변환의 역변환으로 계산하고 y는 확인된 층 바닥 높이를 사용한다. 마커 중심·연결 노드를 사용자의 위치로 대신하지 않는다.

## 렌더 허용과 복구

다음 값은 모두 일치해야 한다: 지도 ID·버전, 현재 층, AR 세션, 정합 ID, 현재 목적지에 연결된 경로 ID·revision. `RenderInput.binding`은 호스트가 보유한 **현재 안내 상태**여야 하며 늦은 경로 응답에서 무조건 새로 만들면 안 된다.

추가 조건은 최신 카메라/앵커 프레임, 정상 추적, 유효 포즈, 검증된 품질 방식·오차·시간·거리·수직축이다. `ArPolicy` 기본값은 없고 QA 검증 식별자와 승인 방식이 없으면 2D를 반환한다. 검출기 픽셀 잔차를 실제 공간 오차로 간주하지 않는다. `src/test/fixtures/ar.ts`의 정책은 시험 분기용이며 현장 승인값이 아니다.

추적 제한·유실은 즉시 숨긴다. grace 안에 복구해도 런타임이 해당 정합을 재검증했다고 명시해야 재사용한다. grace 초과, 품질 실패, 거리·시간 초과, 층 전환은 해당 정합을 폐기한다. 같은 정합 ID로 단계를 되돌려도 살아나지 않는다. 새 정합은 새 ID로 공급한다. 앵커가 유실되면 화살표를 일반 월드 오브젝트로 옮겨 계속 보이지 않는다.

네이티브 호스트의 업데이트 루프는 프레임이 오지 않을 때도 `presenter.tick(nowMs)`를 호출해야 한다. 앱 비활성화·추적 세션 리셋·취소 시 `stop()`으로 즉시 숨긴다. 모든 `*Ms`는 같은 AR 세션의 단조 시계 기준이다. 서버에 보내는 ISO 시각과 혼용하지 않는다.

경로 비동기 결과는 다음 순서로만 적용한다.

1. 목적지 변경·지도/층/AR 세션 변경·재정합 시 최신 문맥을 갱신하거나 `stop()`한다. 목적지 변경 시에도 대기 요청을 먼저 무효화한다.
2. `beginRouteRequest()`의 티켓을 만들고 지원되는 서버 경로를 요청한다.
3. 성공·오류·재시도 콜백 모두에서 `isCurrent(ticket)`을 확인한다.
4. 유효한 결과만 현재 목적지·지도와 대조하여 binding과 경로를 반영한다. 재시도는 새 요청으로 취급한다.

이번 요청 티켓은 **AR 호스트용 기반**이다. 기존 웹 store의 모든 비동기 동작을 교체한 것은 아니다. 네이티브·웹 통합 시 실제 호스트에 적용해야 한다. `ArDiagnostic.eventSeq`는 로컬 순서일 뿐이며 서버 세션 revision이나 서버가 보장하는 이벤트 순서가 아니다.

## 서버와 합의할 제안 — 운영 호출 없음

직접 확인한 서버는 위치 확정에 `manual`·`photo_candidate`, 경로 출발에 `confirmed_node`, 이벤트에 시작·도착·취소만 받는다. 랜드마크도 마커 실제 크기·측량 포즈가 없는 표지판 정보다. 따라서 다음 항목은 구현된 서버 기능으로 부르지 않는다. `src/api/schema.d.ts`와 운영 HTTP 어댑터는 변경하지 않았다.

| 필요한 계약 | 서버·지도 담당과 확인할 내용 |
| --- | --- |
| 마커 메타데이터 | map ID/version, 층, 마커 ID·검출기 종류/패턴, 실제 검출 크기, 중심 위치·앞면 yaw, 설치 제약, 좌표계·측량 근거 |
| 정합 기록 | 클라이언트 UUID, AR 세션, 지도·층, 측정 시각, 변환, 검증 오차·방식. 로컬 렌더와 저장 여부 분리 |
| 마커 위치 확정 | 마커 ID뿐 아니라 현재 카메라 역변환 위치, heading, alignment ID, map version. 명시적 위치 확인 정책 합의 |
| 현재 위치 출발 | 최초·재탐색 모두 `map_position` + floor + ar session + alignment ID 지원. 서버 기록 확인 후 요청 |
| 보행 통로 연결 | 같은 층의 접근 가능한 엣지에 연결, 벽/금지 구역·연결 거리·모호성 검증. 가까운 노드로 무조건 대체하지 않음 |
| 경로 binding | 요청 목적지·지도 버전·경로 revision 보존. 좌표·층 전환 및 재정합 단계 명시 |
| 이벤트 | 추적·층·재정합 이벤트, event_seq 및 route revision/AR session/alignment별 적용 결과·순서 규칙 |
| 지연 결과 | 메시지·사진 작업 순서/취소와 서버 결과 반영 시점의 revision 검증 |
| AI 장애 | 검증된 POI의 직접 선택을 Agent 호출 없이 처리하는 서버 경로 확인 |

지원되지 않는 항목을 기존 API에 필드만 추가해서 보내지 않는다. 서버 계약 구현·OpenAPI 생성·통합 테스트 후 연결한다. 그 전에는 현재 위치 역변환값이 있어도 실제 위치 출발/자동 재탐색 완료로 간주하지 않는다.

## 레이저·LiDAR 없이 수행할 최소 현장 실험

한 층의 짧고 직선인 통로부터 시작한다. 줄자, 실측한 인쇄 마커, 벽·바닥의 기준선, 테이프와 독립 검증점으로 준비할 수 있다. 레이저 거리계나 LiDAR 폰은 필수가 아니다. 다음은 준비 방법이며 측정 정확도가 확보됐다는 뜻은 아니다.

1. 통행 허가가 있는 통로의 바닥 기준점을 원점으로, 통로와 직각인 두 축·위쪽 축을 기록한다. 초기 실험은 자북에 의존하지 않고 로컬 도면축을 사용하며 실제 지도축과의 대응을 명시한다.
2. 벽에 마커를 수직으로 부착한다. 검출기가 요구하는 영역의 한 변을 줄자로 측정한다. 인쇄 용지 전체 크기와 혼동하지 않는다. 마커 중심 높이·바닥 기준점까지의 두 수평 좌표·앞면 방향을 기록한다.
3. 화살표를 놓을 바닥점과 검증용 바닥점들을 **정합에 사용하지 않고** 별도로 실측해 표시한다. 알려진 위치에서 카메라를 다시 비추며 실제 표시점과 화살표의 어긋남을 측정한다. 검출기 잔차만으로 대체하지 않는다.
4. 같은 마커를 거리·각도를 달리해 관측하고, 이동·제자리 회전·가림·앱 중단·AR 세션 리셋을 반복한다. 정합 직후와 이동 후의 위치/방향 오차, 앵커 상태, 시간·거리, 추적 복구를 기록한다.
5. QA가 유효 오차·관측 조건·거리·시간·grace를 결정하고 승인된 `ArPolicy`를 만든다. 첫 OS에서 통과한 조건을 다른 OS에서도 반복한다.

카메라가 바닥을 향하는 동안 수평 heading이 정의되지 않는 자세 등에서는 화살표가 숨겨질 수 있다. 실제 렌더러의 가시성·가림·바닥 깊이 문제도 실기기에서 확인해야 한다. 한 마커의 실험 통과가 역사 전체·층 이동·장거리 드리프트 검증을 대신하지 않는다.

## 검증 기록

`coordinates.test.ts`, `render.test.ts`, `presenter.test.ts`에서 합성 입력으로 52개 검사를 수행했다. 비원점·90도 부호·여러 회전 역변환, 프레임/시각/세션 불일치, 잘못된 크기·기울기, 앵커 갱신, 이동 후 고정 화살표, 현재 위치, 지도/경로/품질 차단, grace 내외, 프레임 공급 중단, 층 전환, 오래된 프레임과 요청 티켓 무효화를 검사한다.

이 검사는 수학·클라이언트 판단과 포트 명령만 증명한다. 실제 영상-포즈 동기 정확도, 검출기 축 변환, 물리 앵커 유지, 벽 관통, 마커 인식 성공률, 현장 오차·드리프트, Android/iOS 동등성, 서버 신규 계약은 **미검증**이다. 전체 로컬 검사·CI 결과는 PR에 기록한다.

2026-10-25 로컬 결과:

- lockfile 변경 없이 전체 의존성 설치 완료. 최초 오프라인 설치의 `pretendard` 누락은 일반 설치로 해결했다.
- `pnpm verify`: 헤더·lint·타입 검사와 41개 파일의 500개 테스트 통과. 기존 언어 테스트가 Node의 Windows 기본 언어에 의존하던 문제는 navigator 조건을 명시하고 브라우저 기본값 검사도 추가하여 해결했다. 제품의 언어 선택 로직은 변경하지 않았다.
